Website Optimization

In plain language

Website optimization is the work of making pages appear and become usable quickly. It is mostly about sending less: fewer files, smaller files, and nothing that blocks the browser from drawing the page.

Speed is not a luxury feature. On a slow connection or an old phone, a heavy page is not merely slower; it is unusable. Optimization is what decides whether people on modest hardware get to use your site at all.

Why it matters

Developers test on fast laptops on fast networks, which is the least representative environment available. Much of the world reads the web on mid-range Android phones over congested mobile networks, sometimes on metered data where every extra megabyte has a price.

The consequences are measurable. Slow pages lose visitors before the content ever appears, and the visitors lost first are the ones with the worst connections, which makes performance a fairness problem, not only a business one. Treat it as an accessibility concern: a page nobody can wait for is a page nobody can perceive.

Performance also tends to decay. Every sprint adds a script, a font, a tracker, an embed, and none of them individually looks expensive. Without a stated budget and a check in the build pipeline, the page gets slower every month and nobody is responsible.

Core guidance

Measure what users feel

Total page weight is a useful proxy, but the metrics that matter describe the experience. Google's Core Web Vitals are the common vocabulary:

  • Largest Contentful Paint (LCP): when the main content becomes visible. Aim for 2.5 seconds or less.
  • Interaction to Next Paint (INP): how quickly the page responds when you tap or click. Aim for 200 milliseconds or less.
  • Cumulative Layout Shift (CLS): how much the page jumps around while loading. Aim for 0.1 or less. This one is also an accessibility issue: content that moves under a reader's finger or cursor causes mis-taps.

Measure both in the laboratory and in the field. Lighthouse in Chrome DevTools gives a repeatable score you can act on; real-user monitoring tells you what your actual visitors experience on their actual devices. Laboratory numbers are for debugging, field numbers are for deciding.

Set a performance budget

A budget is a number written down before the work starts: for example, no more than 150 kilobytes of JavaScript, no more than 500 kilobytes total for a first visit, Largest Contentful Paint under 2.5 seconds on a simulated mid-range phone. Wire the budget into continuous integration so the build fails when a change exceeds it. A budget nobody enforces is a wish.

The most effective optimization is deletion. Ask what a script is for before asking how to make it smaller. Carousels, chat widgets, analytics suites, and font loaders routinely cost more than the whole rest of the page.

Images are the biggest win

Images are usually the majority of a page's bytes, so they are where effort pays best. Four rules cover most of it: choose a modern format such as WebP or AVIF, which are typically 25 to 50 per cent smaller than the equivalent JPEG; never send a 2000-pixel-wide file to display it at 400 pixels; always set width and height so the browser can reserve the space and avoid a layout shift; and lazy-load anything below the fold while eagerly loading the main image.

The critical rendering path

Before a browser can paint, it must build the document tree from the HTML and the style tree from the CSS. CSS therefore blocks rendering by design, and a script in the document head blocks parsing while it downloads and runs.

Keep the CSS small and send it early. Give scripts defer so they download in parallel and run after the document is parsed, or async for independent scripts where order does not matter. Self-host fonts if you use them, and set font-display: swap so text is readable while the font loads, or, as on this site, use the system font stack and download no font files at all.

Caching and compression

The fastest request is the one that never happens. Compress text responses with Brotli or gzip, which typically removes 70 to 80 per cent of the bytes of HTML, CSS, and JavaScript. Then cache aggressively: give files a content hash in the name and serve them with a one-year Cache-Control lifetime, because a name that changes when the content changes makes long caching safe. HTML itself usually needs a short lifetime with revalidation, since its URL does not change.

Going further

Measure before optimising. Intuition about what is slow is unreliable. Record a performance profile, find the actual bottleneck, change one thing, and measure again. Optimising the wrong thing costs time and adds complexity for nothing.

Perceived performance is real performance. A page that shows meaningful content at one second and finishes at three feels faster than one that shows nothing until two and a half. Stream HTML, render the text before the decoration, and reserve space so nothing jumps.

Progressive enhancement is a performance strategy. Server-rendered HTML that works without JavaScript is fast on weak hardware and resilient when a script fails to load. Every feature you build on top of it should be an addition, not a prerequisite.

This site as a worked example. One stylesheet, one deferred script, no images in the page furniture, no web fonts, no analytics, and no third-party requests at all. That is not minimalism for its own sake; it is what a performance budget looks like when it is actually enforced.

Reference material. web.dev publishes the current Core Web Vitals thresholds and measurement guidance; the HTTP Archive's annual Web Almanac shows how real sites compare.
