Responsive Web Design

In plain language

Responsive web design means one website that rearranges itself to suit whatever screen it is shown on: a phone held in one hand, a tablet, a laptop, a large desktop monitor, or a browser zoomed to four times its normal size.

The method is simpler than it sounds. Write the layout for the narrow screen first, use flexible sizes instead of fixed pixel widths, and add rules for wider screens only where the narrow layout stops looking right.

Why it matters

More than half of all web traffic is on phones, and for many readers a phone is the only device they use. A layout that assumes a wide screen does not merely look cramped; it produces horizontal scrolling, overlapping text, and controls that cannot be reached.

Responsive design is also an accessibility requirement, not a separate concern. WCAG success criterion 1.4.10, Reflow, requires content to be usable at 320 CSS pixels wide without scrolling in two directions. That is the same requirement as supporting 400 per cent zoom on a 1280-pixel desktop display, because zooming to 400 per cent leaves a 320-pixel viewport. One technical solution serves a low-vision desktop user and every phone visitor at once, a clear example of the curb-cut effect.

The alternative (a separate mobile site) means two codebases, two sets of content, and two places for things to fall out of date. Responsive design was invented to avoid exactly that.

Core guidance

Start with the small screen

Write the single-column, small-screen layout as your base styles, then add min-width media queries to enhance upward. Doing it the other way round (desktop first, with max-width queries subtracting things) produces more code and more special cases.

Mobile-first also enforces honest prioritisation. If a module cannot justify its place in a 375-pixel column, it rarely deserves prominence at 1440. The narrow layout is where you find out what the page is actually about.

None of this works without the viewport meta tag. Without it, mobile browsers pretend to be about 980 pixels wide and scale the result down, so your media queries never fire and your text is unreadable.

Fluid units, not fixed pixels

Set type in rem rather than px, so a reader who has raised their browser's default text size gets larger text everywhere. Size layout in percentages, fr units, and minmax() so containers adapt. Reach for clamp() when you want a value to scale smoothly between a sensible floor and ceiling.

Constrain the reading measure. Lines longer than roughly 75 characters are hard to track back to the start, which affects everyone and affects dyslexic readers most. A max-width in ch units expresses that directly.

Content-driven breakpoints

Put breakpoints where your content breaks, not at the width of whichever phone was popular the year you built the site. Widen the browser slowly and watch: the moment a line of text gets too long, a card gets too narrow, or a table stops fitting, that is a breakpoint. Device-named breakpoints age badly because devices change and your content does not.

Write media queries in em rather than px, so the breakpoint moves when a reader increases their default text size. And keep the number small: three or four well-chosen breakpoints usually beat a dozen.

Responsive media and code blocks

The baseline rule for images is max-width: 100% with height: auto, so nothing overflows its container. Beyond that, use srcset and sizes to let the browser download the smallest file that will still look sharp, and always declare width and height so space is reserved and the page does not jump.

Some content genuinely cannot reflow. Code samples are the clearest example: wrap a line of code in a different place and you can change what it means. The answer is to let the code block scroll horizontally inside its own container while the page itself never scrolls sideways. That container needs tabindex="0" so a keyboard user can scroll it without a mouse. Wide tables are handled the same way.

Touch, hover, and target size

Hover does not exist on a touchscreen. Anything revealed on hover must also be reachable by focus and by tap, or it is invisible to a large share of your audience. Drop-down menus that open on hover are the classic failure here.

Targets need to be big enough to hit. WCAG 2.5.8 sets a minimum of 24 by 24 CSS pixels; 44 by 44 is the practical target for anything important, with enough space between neighbouring controls that a mis-tap is unlikely. On this site, navigation collapses on narrow screens into a button labelled Menu: a word, not a bare hamburger icon, because unlabelled icons are guesswork for anyone who has not learned that particular convention.

Going further

Container queries ask how much room a component has, rather than how wide the window is. That is usually the question you actually meant: a card in a narrow sidebar should stack even on a wide screen. Support is now broad enough to use with a viewport-query fallback.

Logical properties (margin-inline, padding-block, inset-inline-start) describe position relative to the reading direction rather than to the physical screen. They make right-to-left support close to free, and they cost nothing to adopt.

Test the extremes. Set the browser to 320 pixels wide and confirm there is no horizontal scrollbar. Zoom to 400 per cent and confirm the same. Increase the browser's default font size and check that nothing clips. Then check whether text containers still work when the words get 30 per cent longer, as they do in German or Spanish translations.

Reference material. The Mozilla Developer Network guide to responsive design and the WCAG 2.2 Reflow criterion at the World Wide Web Consortium together cover almost everything on this page in more depth.
