Web Application Security

In plain language

Web application security is the work of stopping other people from reading, changing, or destroying things they should not touch. Most attacks are not clever. They rely on an application trusting something it should not have trusted: a form field, a URL, a cookie, a file upload.

The single idea underneath almost everything on this page: never trust input, and never mix data with code. If you remember nothing else, remember that.

Why it matters

A security failure is not like a layout bug. A misaligned button annoys someone for a moment. A leaked password database follows your users for years, because people reuse passwords, so your failure becomes their bank's failure.

The people harmed are rarely the people who wrote the bug. That asymmetry is what makes security an ethical obligation rather than a technical preference. When you collect data, you accept responsibility for protecting it, which is also the strongest argument for collecting as little as possible. Data you never stored cannot leak.

Security also interacts with accessibility in ways that are easy to get wrong. CAPTCHA is the standard example: it is a security control that locks out many blind users, many users with cognitive disabilities, and plenty of people with neither. There are better options, covered below.

Core guidance

Encrypt everything in transit

Serve every page over HTTPS, which is HTTP carried inside TLS encryption. Without it, anyone between the visitor and your server (a shared network, an internet provider, a compromised router) can read and alter the traffic, including session cookies. Certificates are free from Let's Encrypt, so cost is no longer an excuse.

Redirect all plain HTTP to HTTPS, and then send an HTTP Strict Transport Security header so browsers refuse to use plain HTTP for your domain in future. Mark session cookies Secure so they are never sent unencrypted, and HttpOnly so scripts cannot read them.

Cross-site scripting

Cross-site scripting, abbreviated XSS, happens when text supplied by a user is written into a page in a way that lets the browser treat it as code. An attacker submits a comment containing a script tag; every later visitor runs that script with the full privileges of your site, which means it can read their session and act as them.

The defence is context-aware output encoding: escape data at the moment you put it into the page, using the escaping appropriate to where it lands, because HTML escaping, attribute escaping, URL escaping, and JavaScript escaping are different rules. Modern template engines do this automatically; the vulnerabilities appear where developers deliberately switch it off. In plain JavaScript, the practical rule is to use textContent instead of innerHTML for anything a user supplied.

Cross-site request forgery

Cross-site request forgery, abbreviated CSRF, exploits the fact that browsers attach your cookies to requests automatically. A user who is signed in to your site visits an attacker's page; that page silently submits a form to your site; the browser attaches the session cookie; your server sees a perfectly authenticated request to change an email address or transfer money.

Two defences, used together. First, a synchroniser token: the server puts an unpredictable value in each form and rejects any state-changing request that does not return it, which an attacker's page cannot read because of the same-origin policy. Second, set SameSite=Lax or SameSite=Strict on session cookies so the browser will not attach them to cross-site form posts at all. Also make sure that requests which change state use POST rather than GET, since a GET can be triggered by an image tag.

Injection and input handling

SQL injection is the same mistake as cross-site scripting in a different place: untrusted text is concatenated into a database query and the database interprets part of it as instructions. The fix is parameterised queries, also called prepared statements, which send the query and the values on separate channels so the values can never become syntax.

Validate input on the server as well as in the browser. Client-side validation is a usability feature that helps honest users correct mistakes quickly; it is not a security control, because an attacker simply does not use your form. Prefer allow-lists that describe what is acceptable over deny-lists that try to enumerate every bad thing, because you will never finish the second list.

Authentication and sessions

Never store passwords, even encrypted. Store a hash produced by a slow, purpose-built algorithm (bcrypt, scrypt, or Argon2) with a unique salt per user, so that a stolen database is expensive rather than instantly useful. Never invent your own scheme here.

Length beats complexity. Current guidance from the United States National Institute of Standards and Technology favours long passphrases, checked against lists of known breached passwords, over forced symbol rules and mandatory expiry, both of which push people towards predictable patterns. Offer multi-factor authentication and give session cookies a sensible lifetime, regenerating the session identifier at sign-in.

Finally, make error messages uninformative to attackers but useful to users. "The email address or password is incorrect" avoids confirming which accounts exist, while still telling an honest visitor what to try next.

Why this site uses no CAPTCHA

CAPTCHA is a security control with a serious accessibility cost. Distorted-text puzzles are unusable for many blind users and hard for many users with dyslexia or cognitive disabilities; audio alternatives are frequently worse.

The alternatives are usually adequate and sometimes better: a hidden honeypot field that only automated submissions fill in, a check on how quickly the form was completed, rate limiting by address, and thorough server-side validation. The contact form on this site uses a honeypot and no CAPTCHA.

Going further

Security headers are a large improvement for a small amount of configuration. Content-Security-Policy limits where scripts, styles, and images may load from, and is the strongest second line of defence against cross-site scripting. Strict-Transport-Security forces HTTPS. X-Content-Type-Options: nosniff stops the browser guessing content types. Referrer-Policy limits what your URLs leak to other sites.

Defence in depth assumes each control will eventually fail. Encode output and set a content security policy. Validate in the browser and on the server. Least privilege applies as well: a database account used by a public web page rarely needs permission to drop tables.

Dependencies are your attack surface. Most applications ship far more third-party code than their own. Keep a dependency inventory, patch promptly, and prefer fewer dependencies, which is one reason this site has none at all.

Reference material. The OWASP Top Ten is the standard survey of the most common categories of web application risk, and the OWASP Cheat Sheet Series gives specific, implementable guidance for each one.
