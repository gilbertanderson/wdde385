Self-audit

This site teaches accessibility. That creates an obvious obligation: it should be able to show its own work. This page is that evidence: what is checked automatically, what I checked by hand, and, more importantly, what nobody has checked at all.

Why this page exists

It is easy to write a page about contrast ratios. It is harder to publish the contrast ratios of the page you wrote it on. A resource that explains accessibility while quietly failing it is worse than useless, because it teaches by example that the rules are for other people.

So this page exists to make the claim falsifiable. Everything below can be checked against the source, and the automated portion re-runs on every change whether I want it to or not.

What the automated scan checks

Every push to the repository triggers a GitHub Actions workflow that serves the site and runs pa11y-ci against every page at the WCAG 2.2 Level AA standard. If a page introduces a violation the scan catches, the check fails and I see it.

Here is the actual configuration, the whole thing, not an excerpt:

{
  "defaults": {
    "standard": "WCAG2AA",     // the conformance level being tested against
    "timeout": 30000,
    "wait": 500,               // let JavaScript settle before testing
    "concurrency": 1           // serial: parallel runs hit Chrome protocol errors
  },
  "urls": [
    "http://localhost:8080/index.html",
    "http://localhost:8080/ux-design.html",
    "http://localhost:8080/accessibility.html",
    "http://localhost:8080/security.html",
    "http://localhost:8080/optimization.html",
    "http://localhost:8080/responsive-design.html",
    "http://localhost:8080/contact.html",
    "http://localhost:8080/about.html",
    "http://localhost:8080/self-audit.html"
  ]
}

A deliberate choice worth naming: the accessibility job does not block deployment. A failure shows up as a red check, not a blocked release. That is a weaker policy than the one I would defend in a proposal, and I would rather say so plainly than let the green badge imply something stricter than what is running.

What I checked by hand

Automated tools find roughly a third of WCAG issues. The rest needs a person. These I verified myself, in a browser:

  • Keyboard operability. Every interactive element reachable with Tab, in an order matching the visual layout, with no trap. The skip link is the first focusable element on every page.
  • Focus visibility. A 3px outline with 2px offset on every focused control, never obscured by the sticky header.
  • Contrast, computed from rendered styles rather than from the palette I intended. Body text ranges 15.4:1 to 21:1, links 8.0:1 to 11.5:1, UI borders 4.8:1 and above, across all four themes.
  • Reflow at 320px. No page scrolls horizontally. Code blocks scroll inside their own container, which is the intended behaviour, since code cannot rewrap without changing meaning.
  • Heading structure. One h1 per page, no skipped levels, landmarks on every page.
  • No-JavaScript fallback. With scripting off, the full navigation is visible and every page is readable.

What is not verified

This is the section that matters most, and the one most sites omit.

  • No screen reader testing. Nobody has run this site through NVDA, JAWS, VoiceOver, or TalkBack. Automated tools cannot tell you whether an announcement makes sense, only whether a name exists. This is the largest gap on the site, and it is the reason the accessibility statement claims no conformance.
  • No testing with disabled users. None. Every accessibility claim here is a claim about conformance, not about usability. Those are different things, and only the second one actually matters to the person using the site.
  • Windows High Contrast Mode / forced-colors is untested. The site ships a manual high-contrast theme and honours prefers-contrast, which is not the same as supporting forced-colors properly.
  • Cognitive load and readability are unmeasured beyond readability scoring. Whether a beginner can actually follow these explanations is untested.

A clean automated scan is a floor, not a certificate. The honest summary of this site's accessibility is: it passes the checks a machine can run, and nobody has yet confirmed that a person using assistive technology can get anything done here.

A failure I found and fixed

Worth documenting, because it shows what automated scanning misses.

In the high-contrast theme, the primary button's text resolved to a contrast ratio of 1.66:1, effectively invisible. The cause was a prefers-color-scheme: dark rule leaking into the forced-contrast theme and overriding the text colour but not the background.

/* The bug: the dark-mode rule applied inside the contrast theme,
   so the button kept a light background but got light text too. */

/* The fix: one token, defined in every palette, for text drawn on
   an accent fill, so the pair can never drift apart again. */
:root            { --accent: #1e3a5f; --on-accent: #ffffff; }  /* 11.5:1 */
:root[data-theme="dark"]     { --accent: #9fc4ea; --on-accent: #0b1622; }  /* 10.0:1 */
:root[data-theme="contrast"] { --accent: #000000; --on-accent: #ffffff; }  /* 21:1  */

The point: pa11y did not catch this. The scan runs in the default theme, and the failure only appeared in a theme a user has to opt into. It was found by computing contrast from rendered styles in every theme, a check I had to write on purpose. Anything you do not deliberately test, you are not testing.

Verify it yourself

Do not take any of the above on trust. The fastest checks need no tools at all:

  • Press Tab right now. The first thing to appear should be "Skip to main content". Keep pressing: the focus outline should always be visible.
  • Zoom to 400% (Ctrl/Cmd and +). The layout should reflow to a single column with no horizontal scrolling.
  • Narrow the window to phone width. Same content, same order, nothing truncated.
  • Turn JavaScript off and reload. The site should still work.

To run the automated scan yourself, clone the repository, serve it, and run the same command CI runs:

# serve the site on port 8080
python3 -m http.server 8080

# in another terminal, run the same scan CI runs
npx pa11y-ci --config .github/pa11yci.json

If you find something wrong, I would genuinely like to know: report an accessibility barrier.
