Contact

Use this form to ask a question about anything on this site, suggest a correction, or report an accessibility barrier. There is no time limit, nothing you type is lost if the form finds a problem, and there is no CAPTCHA.

Replies are normally sent within three working days (times shown are US Eastern).

Please read: this is a demonstration form

This site is hosted as static files, so it has no server-side code and nothing is transmitted anywhere. The form validates your entries in the browser and then shows the confirmation you would see on a live site. No message is actually sent, and no data leaves your device.

On a live deployment, submitting this form would post the fields over HTTPS to an endpoint that revalidates every value on the server, rejects submissions that fill in the hidden honeypot field, rate-limits by address, stores the message, and emails an acknowledgement. Client-side validation, on its own, is a convenience for honest users, never a security control. See input handling on the security page for why.

Cannot use this form?

Anyone blocked by this form needs another way to say so, so there is more than one route:

  • Email: ganderson58@student.umgc.edu
  • Issue tracker: open an issue on the project's GitHub repository, which is useful if you can supply steps to reproduce a problem.
  • Course channel: message the instructor through the WDDE 385 classroom, which reaches a person who can escalate a barrier report.

Accessibility reports are acknowledged and, where a fix is made, recorded in the changelog on the accessibility statement. Reports that vanish without acknowledgement teach people to stop reporting.

What this form demonstrates

The form above is the site's main worked example of accessible interaction design. Submitting it empty is the quickest way to see it work.

  • Every input has a real <label> tied to it, not a placeholder standing in for one.
  • Related inputs are grouped in <fieldset> elements with a <legend>.
  • Format hints are attached with aria-describedby, so they are announced before you type rather than only after you fail.
  • Failed fields get aria-invalid="true" and a message that names the fix, preceded by a symbol so colour is never the only signal.
  • An error summary appears at the top, receives focus, and links to each problem field.
  • autocomplete attributes let the browser fill known values, which matters a great deal for people with motor and cognitive disabilities.
  • Correct input types and inputmode mean phones show the right keyboard.
  • A honeypot field replaces a CAPTCHA.
  • At 320 pixels wide, every field is full width and nothing scrolls sideways.
