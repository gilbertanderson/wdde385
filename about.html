About this hub

Who wrote this

I'm Gilbert Anderson, and I already work in tech, so this degree programme at University of Maryland Global Campus is mostly about formalising the web side of what I do rather than starting from nothing. This hub is my coursework for WDDE 385, and it is also where I put things once I actually understand them well enough to explain them to somebody else.

I want to be upfront that these are learning notes and not authoritative documentation, since that distinction matters quite a bit for how you should read anything here. Every page is written from the position of somebody who worked the material out fairly recently and still remembers which parts were confusing, so where I explain why something works the way it does, that explanation is the one that finally made it click for me, which is useful but is not the same thing as a specification. I link the actual specifications throughout, and where the two of them disagree, they are right and I am wrong.

Writing it this way is deliberate, because documentation written by people who have known something for ten years tends to skip the exact step beginners get stuck on, since the author does not remember being stuck there anymore. I still remember, and in my opinion that is the only real advantage these notes have over better sources, so it is worth being honest that it has a shelf life.

The source for everything here is on GitHub at github.com/gilbertanderson/wdde385, including the deployment pipeline and the accessibility checks that run against every change, so you can read the code behind anything described on this site and check whether it actually does what I say it does. There is more of my work at github.com/gilbertanderson.

Outside this coursework I run Strikeworks Studio on my own, building sites for individuals, nonprofits, and small businesses who need a real professional presence without paying agency rates, and I approach that work the same way I approach the pages on this hub, since in my opinion every project starts with the same question a larger UX team would ask, namely who is actually going to use this and what are they trying to get done, before a single line of CSS gets written. I keep coming back to four principles when I structure a page: alignment, meaning a real grid instead of spacing eyeballed into place; proximity, so related things are grouped closely enough that the grouping itself communicates something; contrast, so a reader can tell one section from another without reading every word of it; and repetition, so a multi-page site reads as one coherent thing instead of several pages that happen to share a folder. You can see more of that work, or get in touch, at linkedin.com/in/gilbertanderson.

Scope

The WDDE 385 Web Design Resource Hub is an educational reference covering five areas: user experience design, accessibility and inclusive design, web application security, website optimization, and responsive web design. It was built for WDDE 385: Principles of Web Design and Technology III at the University of Maryland Global Campus.

What is in scope. Introductory guidance on each of the five topics, written in plain language, with commented code samples and pointers to the authoritative specifications. A contact and feedback form. This About page, which holds the accessibility statement, the glossary, and the site map.

What is out of scope. The site is not a substitute for the specifications it summarises, and it is not a certification. It contains no user accounts, no analytics, no advertising, and no tracking of any kind. No user testing was carried out for this project; the testing methods described across the site are methods that would be used, identified as appropriate rather than performed.

The content was written in August 2026 and reflects WCAG 2.2, the Core Web Vitals thresholds current at that date, and the OWASP guidance current at that date. Standards move; check the linked specifications before relying on a detail.

Who this is for

Students in web development programmes, people changing career into front-end development, and working developers who want a quick reference. That audience is global and reads English as a second language in large numbers, so the writing here avoids idioms, expands acronyms on first use on every page, and states dates unambiguously: "March 4, 2026" rather than 3/4/26, which reads as April 3 in much of the world.

It also includes developers with disabilities, who are badly served by technical documentation that is itself inaccessible. That is the reason for the constraint the whole site is built around.

How the site is built

Hand-written HTML, one stylesheet, and one small JavaScript file. There is no build step, no content delivery network, no web font, no client-side framework, and no third-party request of any kind once the page loads. The deployment pipeline is a GitHub Actions workflow that zips the repository and publishes it to Azure App Service, nothing more.

The stylesheet is organised around design tokens in the Material Design 3 sense, meaning color roles, a shape scale, and an elevation scale, each one a plain CSS custom property. I looked at pulling those tokens from Sass rather than writing the property blocks out by hand, and decided against it, since the only thing it would have bought me was fewer repeated lines in the source, at the cost of a real build step in a pipeline that currently has none. That trade was not worth it for a site whose own optimization page argues for exactly the opposite.

That distinction matters to me because a hub that teaches optimization should not ship a bloated page, and a hub that teaches security should be able to point at its own dependency count. A plain, unbuilt styles.css lets me make both claims without a caveat. Pulling in an actual component library would not have.

All content on the site works without JavaScript. The script adds the collapsible navigation, the accessibility settings panel, the copy buttons on code samples, and the contact form's validation. With scripting switched off the navigation list simply stays expanded and the form falls back to the browser's own validation.

AI assistants were used throughout for research and code review: Claude (Opus and Sonnet models) and Cursor's Composer and Grok models.

Accessibility statement

Our commitment

This site aims to conform to the Web Content Accessibility Guidelines (WCAG) 2.2 at Level AA. That target is stated because the site's subject matter makes anything less self-contradicting.

What has been implemented

  • Semantic HTML with banner, navigation, main, and contentinfo landmarks on every page, and a heading hierarchy that never skips a level.
  • A "Skip to main content" link as the first focusable element on every page, visible when it receives focus.
  • Full keyboard operability, with a three-pixel focus outline that is offset from the element so it is never clipped, and no sticky header that could obscure it.
  • Text contrast of at least 4.5 to 1 and user interface contrast of at least 3 to 1, in every theme. Ratios were calculated for each palette rather than estimated.
  • Mobile-first responsive layout using CSS Grid and Flexbox with rem, ch, fr, and clamp(). Usable at 320 CSS pixels and at 400 per cent zoom with no horizontal page scrolling; code samples scroll inside their own containers, which are keyboard operable.
  • Navigation that collapses on narrow screens into a button labelled Menu, with aria-expanded reporting its state.
  • Support for prefers-color-scheme, prefers-contrast, and prefers-reduced-motion, so operating-system settings are honoured without any site-level configuration.
  • An accessibility settings panel for text size, theme and contrast, reduced motion, and link underlining, saved in this browser and applied across the site, with a reset control.
  • A contact form with associated labels, fieldsets and legends, aria-describedby hints, aria-invalid on failure, a focused error summary that links to each problem field, error messages that name the fix, autocomplete attributes, and no CAPTCHA.
  • Breadcrumbs on every interior page, and a "Report an accessibility barrier" link in the footer of every page.

Known limitations

Stating limitations honestly is part of an accessibility statement. As of the last review:

  • The site has not been tested with real screen readers. Testing with NVDA and Firefox, JAWS and Chrome, VoiceOver and Safari, and TalkBack on Android is the next planned step, and no claim of screen reader conformance is made until it is done.
  • No usability testing with disabled participants has been carried out. Automated and expert methods find violations; only testing with people who use assistive technology daily shows whether the site is genuinely usable.
  • Automated scanning with axe, WAVE, or Pa11y is not yet wired into the deployment pipeline. Doing so is described in the project proposal and remains outstanding.
  • The site has not been tested in Windows High Contrast Mode.
  • The "Was this page helpful?" control records nothing, because there is no server. It demonstrates the interaction pattern only.
  • Content is available in English only.

Reporting a barrier

If anything on this site blocks you, please say so. Use the contact form with the "Report an accessibility barrier" category, or email ganderson58@student.umgc.edu if the form itself is the problem. Reports are acknowledged within three working days (US Eastern), and fixes are recorded here.

Glossary

Terms that recur across the site. Each is also defined at its first use on each page, because most readers arrive from a search engine rather than from the home page.

ARIA (Accessible Rich Internet Applications)
A set of HTML attributes that describe roles, states, and properties to assistive technology. It changes what is announced, never what an element does.
CLS (Cumulative Layout Shift)
A measure of how much visible content moves unexpectedly while a page loads. A score of 0.1 or less is the target.
CSRF (cross-site request forgery)
An attack in which another site causes a visitor's browser to send an authenticated request to yours without the visitor intending it.
INP (Interaction to Next Paint)
A measure of how quickly a page responds visibly to a tap, click, or key press. 200 milliseconds or less is the target.
LCP (Largest Contentful Paint)
The moment the largest piece of content in the viewport becomes visible. 2.5 seconds or less is the target.
Landmark
A region of a page (banner, navigation, main, contentinfo) that assistive technology can jump to directly.
POUR
The four WCAG principles: Perceivable, Operable, Understandable, Robust.
Reflow (WCAG 1.4.10)
The requirement that content remain usable at 320 CSS pixels wide without scrolling in two directions.
TLS (Transport Layer Security)
The encryption that turns HTTP into HTTPS, protecting traffic from being read or altered in transit.
WCAG (Web Content Accessibility Guidelines)
The World Wide Web Consortium's accessibility standard. Version 2.2, Level AA, is the target for this site.
XSS (cross-site scripting)
An attack in which text supplied by a user is written into a page in a way that lets the browser run it as code.
